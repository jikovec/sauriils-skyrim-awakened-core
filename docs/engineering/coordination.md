# Coordinating Core and Collection work

GitHub Issues and native blockers own operational state. Check open and closed Issues for overlap before filing. Preserve existing parents and use direct blocking relationships for real prerequisites. An initiative need not close before a dependent issue can reuse an already accepted architectural decision, but an unmet behavioral prerequisite remains a blocker. Report discrepancies to the coordinator, including the exact issue and dependency evidence. Existing milestone and Issue queries are sufficient for the current two-repo foundation. Evaluate a shared board if repeated allocation becomes difficult and a suitable authorized board exists. No second backlog is required.

The coordinator reconciles readiness, assigns scope and writer ownership, checks integration evidence, and resolves architecture or release conflicts within their established authority. Human owners and authorized agents may occupy the role. Workstream ownership follows the source and tests. Native engine and action/quest, runtime stability, local inference, speech, minds and persistence, lore and knowledge, simulation, Collection compatibility, and release engineering can progress independently only when their writers and runtime effects do not overlap.

Use an Issue-scoped branch such as `core/58-actor-identity` or `collection/1-reference-reproducibility`. Use a separate checkout or worktree when another contributor owns the current one. A worktree isolates Git changes; coordinate shared profiles, services, ports and database bindings separately. One authorized writer owns a shared runtime at a time. Preserve concurrent diffs. Use focused commits with issue references. Pair cross-repo PRs with exact dependency revisions and order; use normal protected squash delivery. Keep independent dependency updates separate and record lockfile, license, compile and compatibility evidence before adoption.

A handoff records assigned Issue, repository/branch/base/head, changed files, owning boundaries, exact commands and outcomes, remaining failures, prerequisites, known limits and next action. Record which evidence is local, hosted, installed, gameplay or owner-observed. Keep private inputs and dumps off GitHub. Supply a redacted reference or a local evidence locator through an authorized channel. The PR template captures the public subset.
